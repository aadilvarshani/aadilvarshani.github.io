Detection notes

Detections I'd ship, each written once in Sigma and shown in the languages I've been able to check. Every entry says how each version was verified and where it falls short.

Password spray, then a successful logon

HighT1110.003 Password SprayingWindows Security 4625, 4624

  1. One source IP fails to log on to 10 or more distinct accounts inside 10 minutes.
  2. The same IP then logs on successfully within 30 minutes.
title: Failed network logon
name: failed_network_logon
logsource: {product: windows, service: security}
detection:
    selection: {EventID: 4625, LogonType: [3, 10]}
    condition: selection
---
title: Successful network logon
name: successful_network_logon
logsource: {product: windows, service: security}
detection:
    selection: {EventID: 4624, LogonType: [3, 10]}
    condition: selection
---
title: Password spray from one source
name: password_spray_one_source
correlation:
    type: value_count
    rules: [failed_network_logon]
    group-by: [IpAddress]
    timespan: 10m
    condition: {field: TargetUserName, gte: 10}
---
title: Password spray followed by a successful logon
correlation:
    type: temporal_ordered
    rules: [password_spray_one_source, successful_network_logon]
    group-by: [IpAddress]
    timespan: 30m
tags: [attack.credential-access, attack.t1110.003]
level: high
| multisearch
[ search source="WinEventLog:Security" EventCode=4625 (LogonType IN (3, 10))
| bin _time span=10m
| stats dc(TargetUserName) as value_count by _time IpAddress
| search value_count >= 10 | eval event_type="password_spray_one_source" ]
[ search source="WinEventLog:Security" EventCode=4624 (LogonType IN (3, 10)) | eval event_type="successful_network_logon" ]
| bin _time span=30m
| stats dc(event_type) as event_type_count by _time IpAddress
| search event_type_count >= 2
let spray = SecurityEvent
    | where EventID == 4625 and LogonType in (3, 10)
    | summarize SprayedAccounts = dcount(TargetUserName),
                FirstFail = min(TimeGenerated), LastFail = max(TimeGenerated)
                by IpAddress, bin(TimeGenerated, 10m)
    | where SprayedAccounts >= 10;
spray
| join kind=inner (
    SecurityEvent
    | where EventID == 4624 and LogonType in (3, 10)
    | project SuccessTime = TimeGenerated, IpAddress, TargetUserName, Computer
  ) on IpAddress
| where SuccessTime between (LastFail .. (LastFail + 30m))
| project IpAddress, SprayedAccounts, FirstFail, SuccessTime, TargetUserName, Computer

How each version was checked

  • Sigma: sigma check (sigma-cli 4, pySigma 2) reports no errors and no issues on the full rule. The IDs are trimmed from the version shown here.
  • Splunk SPL: generated from the Sigma rule by pySigma's Splunk backend with the splunk_windows pipeline, shown as generated. The backend can't express temporal_ordered, so this version is the unordered temporal correlation: both steps inside 30 minute buckets, in either order.
  • Sentinel KQL: translated by hand, then parsed and analysed with Microsoft's Kusto.Language library against the SecurityEvent columns it uses. A deliberately misspelt column fails the same check.

Where it falls short

  • The KQL groups failures into fixed 10 minute bins, so a spray that crosses a bin edge is counted in two halves.
  • The Splunk version doesn't enforce order, so a success before the spray also fires.
  • It keys on the source IP. Sprays spread across many IPs need a different detection.

What to tune

  • Shared egress: a VPN concentrator, proxy or NAT gateway puts many users behind one IP. Exclude or raise the threshold for known egress addresses.
  • Scanners and identity tooling that test many accounts on purpose.
  • Service accounts with a stale password retrying across hosts.
  • The thresholds (10 accounts, 10 and 30 minutes) are starting points. I haven't run this against my lab yet; results will go here when I do.
