Race Windows: Why My Process Events Had No Name

The IRQL post ended on race windows, the gap between something happening on a machine and a sensor getting round to looking at it, and I said that would be the next concept. It is, though the example came from closer to home than I expected. My own sensor had been shipping process events with most of their fields empty, and the cause was one of these windows, one I had built myself in user mode before getting anywhere near the kernel.

This post covers where those empty fields came from, the fix I tried first that did not work, and the fix that did, which turned out to be mostly about reading data I already had.

Where the empty fields came from

The sensor gets process launches from ETW (Event Tracing for Windows) using the classic NT Kernel Logger session. I covered the setup in Part 1, so I won't go over it again here. The short version is that Windows calls a function of mine once for every process that starts and hands it an event describing that process.

My callback took one number out of that event, the process ID, and then asked Windows about the process directly: it opened a handle to it and read the image path, the command line (out of the process's own memory, through its PEB, the Process Environment Block), the user it runs as, and its parent. The callback looked like this:

const auto pid = get_event_u32(record, L"ProcessId");
if (!pid) {
    return;
}
// opens the process and asks it for everything else
const ProcessEvent event = build_process_event(*pid);

The gap is between the callback firing and build_process_event opening its handle. If the process has exited in that time, OpenProcess fails and every field that depends on the handle comes back null. For something like cmd /c exit, which lives for a few milliseconds, that happens most of the time.

The name was null too, which I had not expected. It turned out my code only filled in the name by taking the last part of the image path, so when the path lookup failed, the name went with it.

What I tried first

My first fix was in the wrong place. The enrichment code was opening four separate handles to the same process (one each for the path, the command line, the user and a lineage check) and I assumed the problem was a process dying between those calls, which would explain the events where the path was present and the command line was not. So I consolidated them into a single handle, opened as early as possible.

It made events more consistent, but it barely changed how many came back empty. When I spawned forty cmd /c exit processes to test it, nearly every event still had all of its enriched fields null, because in most cases the process was gone before the first OpenProcess call ran at all, and one handle fails just as completely as four.

That test also showed me something I had wrong. A few events had the path and command line null but the user fully filled in, all off the same handle. My current understanding is that Windows tears a dying process down in stages, so its token (which holds the user) can outlive its memory (which holds the command line) for a short while. One handle does not freeze a process in place.

What the event already had

The fix came from looking properly at what ETW was giving me in the first place. An ETW event has two parts. The header is filled in by ETW itself: a timestamp, which provider logged it, an opcode saying what kind of event it is (1 is a process start), and which process and thread were running when it was logged. The payload is a block of bytes written by the provider, which ETW does not interpret.

For process events from the kernel logger, Microsoft documents the payload layout as a class called Process_TypeGroup1. It includes the process ID, the parent process ID, the session ID, the user's SID, the image name and the full command line. TDH (the Trace Data Helper API) reads that layout for you: you ask for a field by name, such as "CommandLine", and it finds it in the bytes.

The kernel writes these fields at the moment the process is created, before my callback runs, so they are there even if the process has already exited by the time I look. My code was reading one of them and throwing the rest away, then going to the live process to ask for the same information again, later, and often too late. Looking back, it is a bit like being handed someone's ID card, reading the number on it, throwing the card in the bin and then chasing them down the street to ask what their name is. Most of the time they had already left the building (and I was the one who designed it that way! 😏).

Decoding the rest of the payload

The change was to decode every field into a small struct first, and only go to the live process for what the payload does not have. Here is the new decoding, in the same callback:

RawProcessFacts facts;
facts.pid             = *pid;
facts.parent_pid      = get_event_u32(record, L"ParentId");
facts.session_id      = get_event_u32(record, L"SessionId");
facts.sid             = get_event_sid_string(record, L"UserSID");
facts.image_file_name = get_event_ansi_string(record, L"ImageFileName");
facts.command_line    = get_event_wide_string(record, L"CommandLine");

const ProcessEvent event = build_process_event(facts);

Each helper handles one type of field rather than one field: ImageFileName is an ANSI string, CommandLine is a Unicode string I convert to UTF-8, and the IDs are plain 32-bit numbers. All of them return an empty value rather than failing if a field is missing, because Microsoft notes that different versions of the event carry slightly different fields. build_process_event now takes the identity from the struct and only opens the process for the full path, the file hashes and the signature check, which need the file on disk and are not in the payload at all.

The SID was the one field that needed care. TDH types it as TDH_INTYPE_WBEMSID, and the comment in the Windows SDK's tdh.h explains that this is a TOKEN_USER structure followed by the SID itself. That structure contains a pointer, so its size depends on whether the process that logged the event was 32-bit (8 bytes) or 64-bit (16 bytes), which the event header records in its flags. I skip that header using the size the flags give me and pass the rest to ConvertSidToStringSidW, so I never parse the SID's own bytes myself. TDH also has TdhFormatProperty, which would have formatted the SID for me, but it needs the full event schema from TdhGetEventInformation, and every other field here was a simple lookup by name, so I chose to keep the SID consistent with the rest rather than pull in the schema machinery for one field.

One thing I wanted to check rather than assume was whether ImageFileName is a full path or just a name. In my captures it is just the name (cmd.exe), so the full path still has to come from the live process.

Before and after

I did this in the wrong order. I built the fix, ran it and captured the "after" first, and only then realised I had no "before" from the old code to compare it with. To get one, I stashed my changes in git, rebuilt the old code and ran it again on the same machine, which at least means the before and after are the exact same source tree with and without the change.

With the old code, I captured about five seconds of ordinary background activity, nothing deliberate. 98 process events came in, and 93 of them had no name at all. This is one of them, trimmed to the relevant fields:

"process": { "pid": 3696, "name": "", "cmdline": null,
             "path": null },
"parent":  { "pid": 0, "name": "" }

The process ID is the only thing that event knows. With the new code, a deliberate cmd /c exit, again trimmed:

"process": { "pid": 23248, "name": "cmd.exe",
             "cmdline": "C:\windows\system32\cmd.exe /c exit",
             "session_id": 1, "path": null, "sha256": null },
"parent":  { "pid": 10900 }

The name, command line, parent, session and user SID are all there. The path and hash are still null, which is expected: they are not in the payload, and by the time the sensor asked for them the process had gone.

The other thing I noticed was that none of this was obvious from the console. Scrolling through the events in my dashboard, I barely saw any empty ones, because most of what runs on a normal machine is long-lived (browsers, updaters, editors) and those get fully enriched without any trouble. The empty events only showed up in numbers when I went looking at short-lived processes specifically.

What this means for detection

The processes that lost the race were the short-lived ones, which is also the shape of a lot of attacker activity: a script or a chain of LOLBins (living-off-the-land binaries, the signed tools that ship with Windows) that each start, do one thing and exit. With the old code, those were exactly the events most likely to arrive with nothing in them. I have not tested this against a real attack chain yet, so I would treat it as a likely blind spot rather than a demonstrated one, but the mechanism does not care whether the short-lived process is benign or not.

With the payload decoded, the name and command line for those processes are now captured however quickly they exit. The path and the hashes are still fetched live, so they still lose the race.

What this does not fix

  • File path, hashes and signature for short-lived processes (still need the process or file to exist when asked)
  • Parent name, which still comes from a live process snapshot and can occasionally be resolved for the wrong process
  • Whether the parent ID can be trusted at all (below)

The last one is the open question I care about most. The payload's parent ID is the parent the process was created with, and that is something a process can choose: Windows lets you create a process with a different parent than yourself (parent PID spoofing), and it is a well known technique. I do not know yet whether this event gives me any way to see the real creator. The header records which process was running when the event was logged, and I suspect that for a process start it is the real creator rather than the claimed parent, but I have not tested it.

Next steps

The next thing I am working on is exactly that test: compare the header's process ID with the payload's parent ID, first on normal launches and then with a spoofed parent, and see whether they diverge. If the header holds up, the sensor gets a creator that is harder to lie about. If it does not, that is a good argument for the kernel callback, which is where this project is heading anyway.
