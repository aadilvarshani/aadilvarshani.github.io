ReaperWatch

A Windows EDR, built from scratch, one real mechanism at a time: a C++ agent that watches process creation as Windows reports it through ETW, and a console that turns that telemetry into alerts.

Why build one when EDRs already exist

I wanted the mechanical answer to a question detection engineering usually leaves as a black box: how does an EDR find out a process exists, with enough detail to judge it, as close to the moment it happens as Windows allows? Not the detection logic, the layer underneath it. ReaperWatch is me building that layer myself, in the open, including the parts that didn't work the first time.

NT Kernel Logger

Windows' own process trace session. ReaperWatch doesn't poll for processes: the kernel reports every creation through ETW as it happens.

1ETW consumer

The agent starts the NT Kernel Logger in real-time mode with the process flag set, so every process creation on the machine arrives as an event while it happens, not from a poll.

std::vector<BYTE> buffer(size, 0);

2Process monitor

Each event gets its command line from the PEB, SHA256 and MD5, the Authenticode signer, user context and two levels of lineage. A parent is only recorded if it provably started before the child, so a recycled PID never gets blamed for something it didn't launch.

// PID-reuse guard: a real parent must be no younger than its child. If the
    // PID was recycled, the process now holding it started later -> reject it.
    const auto child_time = get_process_creation_time(pid);
    const auto parent_time = get_process_creation_time(parent_pid);
    if (!child_time.has_value() || !parent_time.has_value()) {
        return;  // can't verify -> don't record an unverified parent
    }
    if (*parent_time > *child_time) {
        return;  // parent started after the child: PID reused, impostor
    }

3Event sink

Events are appended to a local JSON Lines file, whether or not anything is reading it. Writes are serialised in case ETW calls back from more than one thread, and a failed write never takes the sensor down.

void append_event_line(const std::string& json_line) {
    std::lock_guard<std::mutex> lock(g_mutex);

    std::error_code ec;
    std::filesystem::create_directories(kDataDir, ec);  // no-op if it already exists

    // Reopen-per-call keeps this simple and crash-safe (no long-lived handle to
    // leak or corrupt); fine at process-creation rates.
    std::ofstream file(kEventsFile, std::ios::app | std::ios::binary);
    if (!file) {
        return;  // best-effort: never crash the sensor over a logging failure
    }
    file << json_line << '\n';

4HTTP sender, optional

If a config file sits next to the agent, each event is also POSTed to a console over WinHTTP, authenticated with a per-console key. No config file means fully local: no network calls at all.

5events.jsonl

One JSON line per process event, always the same shape: process, parent, grandparent, user, host and flags. A missing value is written as null rather than dropped, so every event has every key.

6Ingestor

The console tails the file by byte offset into SQLite. A half-written last line is left for the next pass, and a malformed line is consumed and skipped so it can't block everything behind it.

7SQLite

Node's built-in node:sqlite, so there's no native dependency to compile. It stores the full enriched event plus a raw_json column for drill-down.

8EQL engine

Every event runs through every rule. One event can raise several alerts, and a rule whose query throws is logged and skipped instead of stopping the pass.

function matchEvent(evt) {
  const alerts = [];
  for (const rule of RULES) {
    let hit;
    try {
      hit = EQL.matches(rule.query, evt);
    } catch (err) {
      console.error(`[detection] rule '${rule.name}' query error:`, err.message);
      continue;
    }
    if (hit) {
      alerts.push({
        ts: evt.timestamp,
        severity: rule.severity,
        mitreId: rule.mitreId,
        mitreName: techniqueName(rule.mitreId),
        ruleName: rule.name,
        title: rule.title,
        detail: (evt.process?.cmdline || evt.process?.path || '').slice(0, 200),
      });
    }
  }

9Ruleset

Rules are data, not code: a query, a severity and an ATT&CK ID. Adding a detection is one entry. Eleven ship in the current build.

Endpoint telemetry

What it sees on the machine.

  • Sees every new process through ETW, with its command line, hashes, signer, user, parent and grandparent1
  • Gets the details right, including who really started a process when Windows starts it on someone's behalf1.5
  • A kernel driver that sees processes, threads, loaded images and drivers, and handle access as they happen2
  • Knows the real parent even if an attacker turns ETW off2
  • Notices if someone blinds the sensor or kills the agent2
  • Network connections and DNS lookups3
  • File and registry changes3
  • Script content through AMSI, named pipes and WMI3
  • Services, scheduled tasks, logons and USB drives3
  • When a service, task or WMI starts a process, links it back to whoever asked for it3
  • Hard to tamper with: protected service, a properly signed driver, TLS and auto-updates7
  • Flags vulnerable software and risky settings on each machine7

AI security

What AI agents do on the machine.

  • Tags every process an AI agent starts, however deep it goes1.5
  • Matches the agent's own log of each tool call to the process it caused1.5
  • Tighter blocking for anything an agent starts2
  • Lists every AI agent, coding CLI, IDE plugin, MCP server and local model on the machine8
  • Flags AI tools, local models and API keys that policy doesn't allow8
  • Watches AI chats on work devices for sensitive data in prompts and uploads8
  • Catches prompt injection that leads to a real action, poisoned MCP tools, poisoned agent memory, and data or credentials leaving through an agent8
  • Compares what the agent said it ran with what actually ran8
  • Maps detections to MITRE ATLAS and the OWASP Top 10 for agentic apps8
  • Red teams the agents on the machine with injected content, poisoned tools and malicious packages8
  • Judges each attack by what the agent actually did, uses honeytokens to prove data left without harm, and turns each working attack into a signature8
  • AI agents that play the attacker against ReaperWatch to find what it misses8

Research and emulation

How each signature gets made.

  • Starts from vendor research, threat reports or my own testing, and every signature links to its write-up4
  • I run each technique in a lab, record what it leaves behind, and build the signature from that recording4
  • Every signature is replayed against recorded attacks on every build4

Normalized telemetry and storage

Every event in one shape.

  • SQLite, with every event in the same JSON shape1
  • Schema v2: an ID for each process that survives PID reuse, its parent and grandparent, and the process that started the whole chain1.5

Query engine

Rules that search stored events.

  • 11 EQL rules, each with a severity and an ATT&CK ID1
  • Rules that run on a schedule and alert when they match5
  • Rules that follow a sequence of events, across event types and machines5
  • Sigma rules run on ReaperWatch data5
  • New rules and indicators run back over old data5
  • Rules live in version control and get tested on recorded data before they go out5
  • Threat intel indicators matched live and against history7

Signature engine

Detections that run live on the machine.

  • Runs inside the agent on live events and remembers what each process tree has done4
  • One signature per technique with a clear name, like parent PID spoofing, LSASS access or remote thread injection4
  • Follows a chain across a process tree, like a dropper, then persistence, then a callback4
  • Checks memory when behaviour looks off, like an image that doesn't match its file, or code running from memory with no file behind it4

Identity, deception and memory

What a process view misses.

  • AD and Kerberos attacks like Kerberoasting, DCSync and golden or silver tickets, seen from endpoints and domain controllers9
  • Planted fake files, credentials and tokens. Anyone touching them sets off an alert9
  • Memory scans with YARA, on demand or when behaviour looks off9

Prevention and response

Stopping an attack and cleaning up after.

  • Stops a process before it starts, and limits handle access2
  • Signatures I trust enough block the process or kill the tree4
  • Kill a process tree, quarantine files, cut the machine off the network, roll back changes7
  • Remote shell, evidence collection and memory capture7
  • USB control and app allow and deny lists7

Alert processing and AI triage

Where every alert goes.

  • Alerts with a severity and an ATT&CK mapping1
  • Alerts from both engines arrive in one format6
  • Each alert gets the process tree, user, host, file reputation and threat intel attached6
  • Related alerts are grouped into one incident, deduplicated and scored6
  • Incidents go where you want them: DFIR-IRIS, a SIEM, chat or a webhook6
  • AI summarises each incident, suggests a verdict, cites the evidence and lists next steps6
  • Rules decide what gets escalated or closed, an analyst approves, and their feedback improves triage6

Console and fleet

Where you work.

  • Overview, Detections and Hunt, and hunting uses the same EQL as the rules1
  • Engines, signatures, rules, enrichment and outputs all set from the console6
  • Many machines, with policies per group and staged rollouts7

macOS and Linux

The same thing on Mac and Linux.

  • macOS: events from Apple's Endpoint Security framework and the unified log10
  • Same schema, parents and chains as on Windows10
  • Signatures for TCC abuse, launch agents, Gatekeeper bypass and keychain access10
  • Blocking through Endpoint Security, with the same engines and alert pipeline10
  • Linux: an eBPF sensor for processes, files and network, with LSM BPF for blocking11
  • Container and Kubernetes details on every event11
  • Signatures for privilege escalation, cron and systemd persistence, and rootkits11
  • Same schema, engines and pipeline11
